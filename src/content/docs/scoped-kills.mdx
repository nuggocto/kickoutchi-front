Most port janitors kill one PID, and that's still Kickoutchi's default. Scoped kills are for when
one PID isn't the whole mess: dev servers with workers, package runners, agent shells, file
watchers, and process groups that leave orphans behind.

<Callout type="safety" title="Default kill is unchanged">
  `kick kill --port 3000` and `kick kill --pid 18422` still target exactly one confirmed PID. You
  only get a wider scope when you ask for it: `--tree`, `--group` (Linux and macOS), or the TUI's
  `t` / `T` keys (Linux and macOS).
</Callout>

## Inspect first

`inspect` is read-only; it never signals anything. Use it to see whether the port's owner is the
real root, whether a parent supervises it, and, on Linux and macOS, whether members of its process
group sit outside its tree.

<CommandBlock
  code={"kick inspect --port 3000\nkick inspect --pid 18422"}
  label="read-only family view"
/>

The report shows:

- The target PID, command line, visible ports, and on Linux/macOS the process group.
- Ancestors nearest-first, so supervisors and package runners are visible.
- Siblings under the same parent.
- The bounded descendant tree, with ports on members that own sockets.
- Process-group members on Linux/macOS, marking members outside the tree.
- A suggested `kick kill --pid <root> --tree` command, and on Linux/macOS a `--group` command only
  when group scope would catch processes the tree would leave alive.

## Tree kill

A tree kill targets the confirmed root and its descendants. Reach for it when a stale dev server
owns the port and has workers underneath it.

<CommandBlock
  code={
    "kick kill --port 3000 --tree\nkick kill --pid 18422 --tree\nkick kill --pid 18422 --tree --force"
  }
  label="tree scope"
/>

An interactive tree kill asks you to type `tree`, or `force` for a force kill. A protected root
still needs its PID or name typed first. A protected descendant refuses the whole tree.

On Linux and macOS, Kickoutchi freezes the tree before it signals anything:

- Re-check the confirmed root right before acting.
- Count the tree before any signal; a tree over the limit is refused with no side effects.
- `SIGSTOP` the root first, then sweep descendants to a fixed point.
- Verify each stopped member's identity before delivering a terminating signal.
- Send `SIGTERM`, then `SIGCONT`, leaves first and root last. `--force` sends `SIGKILL` instead.
- If anything becomes uncertain before delivery, resume only processes Kickoutchi stopped and
  send no termination. Processes that were already stopped stay stopped on abort.

A cleanup error after a thaw names only the processes whose `SIGCONT` was refused, since those may
still be stopped. A member that exited while frozen can't be resumed, so it isn't reported as a
thaw failure.

Windows has no `SIGSTOP`, so a tree kill there contains the tree in a Job Object instead:

- Re-check the confirmed root and tree before the Job Object commit.
- Refuse before commit for unsafe PIDs, protected descendants, incomplete metadata, identity
  changes, or a tree over the limit.
- Assign the root to a Job Object. That's the point of no return. Then bring the descendants into
  the same job. Children that members start after that join the job automatically.
- Prove the final job membership, identities, and names again, and re-apply the warning check for
  `--yes`, before termination. A late child that needs fresh review, or a tree that keeps
  changing during this check, withholds the whole termination.
- Terminate nothing if a live member can't join the job. Killing that process on its own would
  leave a gap in the containment, so nothing is signalled.
- Terminate contained members with `TerminateJobObject`. Windows tree termination is hard
  termination only.
- Report delivered, already exited, unconfirmed, and not terminated PIDs separately instead of
  calling them all a success, and skip `TerminateJobObject` when a containment check after commit
  fails.

## Process-group kill

A group kill targets every visible process in the target's POSIX process group. It's CLI-only, on
Linux and macOS, and covers what a descendant tree can't: double-forked helpers, reparented workers,
or runaway trees where the process group is the truer boundary.

<CommandBlock
  code={
    "kick kill --pid 18422 --group\nkick kill --port 3000 --group\nkick kill --pid 18422 --group --force"
  }
  label="group scope"
/>

A group kill reaches wider than a tree kill, so it asks more of you:

- It conflicts with `--tree`.
- It lists every visible member before confirmation.
- It warns that process groups can include unrelated commands from the same shell.
- It asks you to type `group` or `force`, unless you pass `--yes` and the group clears the stricter
  all-clear check.
- In a normal termination, every `SIGTERM` is queued before any stopped member resumes, so a
  parent-like member can't wake up and start survivors while its siblings are still frozen.

## TUI support

On Linux and macOS the TUI offers tree kills. Windows has CLI `--tree`, but its TUI leaves out the
tree keys:

| Key | Action                               |
| --- | ------------------------------------ |
| `x` | Terminate the selected process only  |
| `X` | Force-kill the selected process only |
| `t` | Terminate the selected process tree  |
| `T` | Force-kill the selected process tree |

The tree preview loads in the background, so the table stays responsive. The preview is for your
eyes only. When you confirm, Kickoutchi collects the tree again, re-checks the root, and refuses if
the fresh tree no longer passes the same checks.

## Windows specifics

Windows has read-only `inspect` and CLI `kill --tree`. A normal `kick kill` still targets exactly
one confirmed PID, and `--group` doesn't exist, because Windows has no POSIX process groups.

Kickoutchi trusts a Windows parent link only after checking process creation times. If missing data
could hide a descendant inside the confirmed tree, `--tree` refuses with an incomplete-metadata error
instead of quietly leaving that process out. Native Windows collection also cannot see individual Linux
processes inside WSL2; use the Linux build inside WSL2 for those trees.
