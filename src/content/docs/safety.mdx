A port can change owners between the moment you look and the moment you kill. Kickoutchi resolves
and checks the target again before signalling it. This page lists those checks and their limits.

## Confirmations

Nothing is terminated without a confirmation, and what you type grows with the risk:

- Normal kill: type `y`.
- Force kill: type `force`, unless you set `confirm_force_kill = false`.
- Tree kill: type `tree`, or `force` for a force tree kill.
- Group kill: type `group`, or `force` for a force group kill.
- Protected process: type its PID or its process name. The name is offered only when it can be
  typed exactly as shown, and an empty answer never confirms.

Before any prompt, Kickoutchi prints the target, the affected ports, the equivalent shell command,
and any warnings.

<Callout type="safety" title="--yes skips the question, not the safety">
  `--yes` skips the normal prompt for a target you trust. It still prints the banner and every
  warning, and it can never skip protected-process confirmation. For tree and group kills, the fresh
  scan at execution time must still be all-clear; if the scope changed into something that needs
  your review, Kickoutchi refuses and signals nothing.
</Callout>

## Hard limits

- PID 0, PID 1, Kickoutchi's own PID, and the Windows System process (PID 4) can't be targeted at
  all.
- `kill --port` refuses a port two PIDs share. It lists the candidates and makes you pick one with
  `--pid`.
- A port with no readable owner can't be killed. Kickoutchi exits `4` (permission denied) rather
  than act on incomplete information.
- On Linux, when Kickoutchi can't read every process on the host, `kill --port` behaves like this:
  - If the port has no readable owner, it refuses before any prompt and exits `4`.
  - If two or more visible PIDs own the port, it refuses and lists them.
  - If the port has exactly one verified owner and only unrelated processes are unreadable, it
    prints a note and targets that owner. Before sending, it checks the port again and refuses if a
    second visible owner appeared. Afterwards it checks whether the port cleared.
- With several targets, Kickoutchi resolves and authorizes every one before asking anything. A
  single refusal stops the whole batch before the prompt, and protected processes must be killed on
  their own. After you confirm, it re-checks each target against a fresh snapshot. A target that
  changed is skipped and sets the exit code, without blocking the others.
- Tree and group kills have size limits. A tree or group over the limit, or one that keeps changing,
  is refused rather than partly killed.

## Protected processes

Some processes hold everything else up: init, your database, Docker, core OS services. These are
protected. Killing one means typing its PID or name, and neither `--force` nor `--yes` can shortcut
that. The built-in list includes Docker processes such as `dockerd`, `docker-proxy`, and
`com.docker.backend`, and you can [add your own names](/docs/config#protected-processes).

On Linux, the kernel can cut a process name in the middle of a Unicode character. Kickoutchi decodes
that cut name the same way when listing, matching protection, and running the final check, so a
truncated character alone doesn't block a kill; the ownership and identity checks still apply.

On macOS, a configured name also matches the executable's file name exactly. Tree and group kills
and `inspect` apply that rule to the root and every descendant, from planning through the final
check before any signal.

Everything shown to a person is sanitized first. Names, paths, and status text from the OS lose
control bytes, ANSI escapes, bidi controls, and zero-width characters before they reach your
terminal.

## The target can't wander off

This is the important one. After you confirm, Kickoutchi checks the target again right before it
signals:

- It collects ports again and checks the confirmed target still matches.
- If the port's owner changed, it stops, and nothing is sent.
- If the owner became unreadable, it stops with "ownership unavailable" (exit `4`).
- If the target became protected in the meantime, it stops (exit `6`).

A normal kill only ever signals the PID you confirmed. A tree or group kill only signals the scope
you confirmed, after a fresh scan and verification.

## Tree and group kills on Linux and macOS

Tree and group kills are ogre-sized: they reach past one PID, so they go through stricter steps:

- You opt in with `--tree`, `--group`, or the TUI's `t` / `T` for a tree.
- Kickoutchi counts members before signalling anything, so a refusal over the limit has no side
  effects.
- It freezes the root first, then sweeps the members until the set stops changing.
- It checks each member's identity once it's stopped, when its PID can't be recycled, and keeps that
  identity for rollback, so a recycled PID gets resumed, never signalled.
- It thaws everything on any refusal, permission problem, identity change, protected descendant, or
  incomplete metadata. A cleanup error names only the processes whose `SIGCONT` was refused.
- A group kill queues every `SIGTERM` before any `SIGCONT`, so a parent-like member can't wake up
  early and start survivors.

[Scoped kills](/docs/scoped-kills) walks through the full flow.

## Tree kills on Windows

Windows tree kills contain the tree in a Job Object instead of freezing it first:

- Kickoutchi checks the confirmed root and the tree it saw before assigning anything to the Job
  Object.
- It refuses before that point for unsafe PIDs, protected descendants, incomplete metadata, identity
  changes, or a tree over the limit.
- Assigning the root to the Job Object is the point of no return. Any child a member starts after
  that joins the job automatically.
- Before terminating the job, it proves the final membership, identities, and names again, and
  re-applies the warning check for `--yes`.
- If a live member can't join the job, it terminates nothing, rather than kill that process on its
  own and leave a gap in the containment.
- It terminates the contained members outright and reports delivered, already exited, unconfirmed,
  and not terminated members separately.
- It refuses when missing creation-time data could hide a descendant inside the confirmed tree.

## Platform details

In a nested Linux PID namespace, a process outside the namespace may still hold the same socket.
Kickoutchi marks that ownership as partial and refuses to kill when it can't complete the required
ownership checks, even if one owner is visible.

| Platform | How termination stays honest                                                                                                                          |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| Linux    | Delivers through `pidfd` (kernel 5.3+). Tree and group kills open pidfds before `SIGSTOP`, then reuse them to thaw and for the final signals.         |
| macOS    | No pidfd, so tree and group kills stop, then verify: once a process is stopped, its verified PID can't be recycled before the signal lands.           |
| Windows  | Process handles for exact single-PID termination, and Job Objects for CLI tree kills. `inspect` works; `--group` and the TUI's `t` / `T` don't exist. |

## After the kick

After a termination, Kickoutchi collects ports once more and reports whether the confirmed ports
disappeared.

The [exit codes](/docs/commands#exit-codes) show how each of these outcomes reaches a script.
