The swamp shortcut: use the CLI when you already know which port to clear. CLI
commands **never** open the TUI • they print to stdout/stderr and exit with a
[stable code](/docs/commands#exit-codes).

There are five subcommands on every platform: `list`, `inspect`, `kill`, `watch`, and `why`. Only
`kill` ever signals anything. Windows supports read-only `inspect` and CLI `--tree`; `--group`
stays Linux/macOS-only. Use whichever binary you like • `kick` is shorter.

## Listing ports

<Terminal
  title="kick list"
  lines={[
    { kind: "command", text: "kick list" },
    { kind: "muted", text: "PROTO  ADDRESS    PORT  PID    PROCESS   STATE   LABEL" },
    { kind: "output", text: "TCP    127.0.0.1  3000  18422  node      LISTEN  web dev" },
    { kind: "output", text: "TCP    127.0.0.1  5173  18510  vite      LISTEN  -" },
    { kind: "output", text: "TCP    0.0.0.0    5432  1201   postgres  LISTEN  postgres" },
  ]}
/>

The table is plain, whitespace-separated text with no box-drawing • so it stays friendly to
`grep` and `awk`. Withheld metadata shows as `-`. The `LABEL` column appears once you've configured
[endpoint labels](/docs/config#endpoint-labels).

Human-readable endpoints retain IPv6 interface scope, for example `[fe80::1%3]:5353`, throughout
the list table, TUI, inspect, watch, Why, search, diagnostics, and kill confirmations. Legacy
`list --json` remains unchanged; versioned structured output carries scope separately.

### Narrowing the list

<CommandBlock
  code={
    "kick list --port 3000\nkick list --process node\nkick list --filter scope:public\nkick list --filter 'label:web family:ipv4'\nkick list --sort pid"
  }
  label="list options"
/>

- `--port PORT` • only the rows bound to one exact port.
- `--process TEXT` • rows whose process name contains the text.
- `--filter TEXT` • TUI-style search text or structured filters (see [filters](/docs/commands#filters)).
- `--sort MODE` • `port`, `pid`, `protocol`, `process`, `parent`, or `scope`.

## JSON for scripts

`list --json` prints a stable, documented shape • the field names and enum casing are a contract,
so it's safe to parse.

<Terminal
  title="kick list --port 3000 --json"
  lines={[{ kind: "command", text: "kick list --port 3000 --json" }]}
/>

```json
[
  {
    "protocol": "tcp",
    "local_addr": "127.0.0.1",
    "local_port": 3000,
    "state": "listen",
    "pid": 18422,
    "process_name": "node",
    "executable_path": "/usr/bin/node",
    "command_line": "node server.js",
    "parent_pid": 18001,
    "parent_process_name": "cursor-agent",
    "child_pids": [],
    "protected": false,
    "platform": "linux",
    "permission": "full",
    "label": "web dev"
  }
]
```

Missing metadata is `null`, never an empty string. An empty result is always `[]`.

For the complete in-scope observation • every native TCP state, owner identity, completeness, and
evidence gap • use `--snapshot-json` instead:

<CommandBlock code={"kick list --snapshot-json"} label="full snapshot" />

Snapshot mode deliberately ignores `--port`, `--process`, `--filter`, `--sort`, and
`hide_system_processes`, and omits full command lines. See
[Structured output](/docs/structured-output).

## Killing by port or PID

`kill` needs **exactly one** target • a `--port` or a `--pid` • and asks before it does anything.

<Terminal
  title="kick kill --port 3000"
  lines={[
    { kind: "command", text: "kick kill --port 3000" },
    { kind: "output", text: "Terminate PID 18422 (node)" },
    { kind: "output", text: "Ports: TCP 127.0.0.1:3000" },
    { kind: "output", text: "Command: kill 18422" },
    { kind: "muted", text: "Type y to confirm, or press Enter to cancel: y" },
    { kind: "success", text: "sent SIGTERM to PID 18422 (node)" },
    { kind: "success", text: "confirmed target ports are no longer visible" },
  ]}
/>

<CommandBlock
  code={
    "kick kill --port 3000\nkick kill --pid 18422\nkick kill --port 3000 --yes\nkick kill --pid 18422 --force"
  }
  label="kill examples"
/>

- `--force` • stronger force confirmation; Unix uses `kill -9`, while Windows delivery is hard
  termination either way.
- `--yes` • skip the **normal** prompt for a target you already trust.

<Callout type="safety" title="What --yes does and doesn't do">
  `--yes` opts out of being *asked*, not of being *told*. The target banner and every safety warning
  still print, and it **cannot** bypass protected-process confirmation. Protected targets with
  `--yes` exit with code `6` and signal nothing.
</Callout>

## Inspecting a process family

`inspect` is the read-only way to choose the right root before a scoped kill. It shows ancestors,
descendants, siblings, command lines, ports, and suggested tree commands. Linux/macOS also show
process-group members and `--group` hints.

<CommandBlock
  code={"kick inspect --port 3000\nkick inspect --pid 18422"}
  label="inspect examples"
/>

## Tree and group scope

Normal kill still targets one PID. `--tree` adds descendant cleanup on Linux, macOS, and Windows;
`--group` is the Linux/macOS-only POSIX process-group scope:

<CommandBlock
  code={"kick kill --port 3000 --tree\nkick kill --pid 18422 --tree\nkick kill --pid 18422 --group"}
  label="scoped kill examples"
/>

- `--tree` • terminate the target and its descendants. Type `tree` to confirm, or `force` with
  `--force`.
- `--group` • terminate every visible member of the target's POSIX process group. Type `group` to
  confirm, or `force` with `--force`.
- `--tree` and `--group` conflict; pick one scope.
- Windows rejects `--group` and does not expose TUI `t`/`T` tree keys. Windows CLI `--tree` uses
  Job Object containment and hard termination.

See [Scoped kills](/docs/scoped-kills) for the Unix freeze-first and Windows Job Object safety
details.

## Watching and explaining

Two read-only commands answer questions `list` can't:

<CommandBlock
  code={
    "kick why 3000\nkick why 3000 --all-protocols --all-addresses --json\nkick watch --tcp --port 3000\nkick watch --filter state:listen --duration 30s --json"
  }
  label="watch and why"
/>

- `why PORT` • takes one snapshot, then attempts the exact bind and closes it immediately. It tells
  occupied, permission denied, address unavailable, and unsupported apart, with the evidence behind
  each verdict.
- `watch` • polls full-state snapshots and streams `baseline`, `bind`, `release`, `replacement`, and
  `collection_gap` events, as terminal output or NDJSON.

Neither one signals a process or runs Docker. Full walkthrough:
[Watch & Why](/docs/watch-and-why).

## How the CLI behaves

- **An empty unfiltered list is success** (exit `0`) • a quiet machine isn't an error.
- **An empty filtered result is no-match** (exit `3`) • so `kick list --port 3000 && echo busy`
  works as an occupancy probe.
- **`kill --port` refuses ambiguous ports** • if two PIDs own one port, it lists the candidates and
  asks you to pick with `--pid` instead of guessing.
- **A port with no readable owner** exits `4` (permission denied) rather than pretending it can act.

When a `--port` lookup finds no socket but a process _mentions_ that port on its command line,
Kickoutchi prints a "possible related process" hint to **stderr** so JSON on stdout stays clean.
