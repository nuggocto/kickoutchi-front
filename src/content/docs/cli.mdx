Give `kick` a subcommand and you stay in the CLI; it never opens the TUI. Commands print to stdout
or stderr and return a [stable exit code](/docs/commands#exit-codes).

Every platform has five subcommands: `list`, `inspect`, `kill`, `watch`, and `why`. Only `kill`
ever signals anything. Windows has read-only `inspect` and `kill --tree`; `--group` is Linux and
macOS only. `kick` and `kickoutchi` are interchangeable.

## Listing ports

<Terminal
  title="kick list"
  lines={[
    { kind: "command", text: "kick list" },
    { kind: "muted", text: "PROTO  ADDRESS    PORT  PID    PROCESS   STATE   LABEL" },
    { kind: "output", text: "TCP    127.0.0.1  3000  18422  node      LISTEN  web dev" },
    { kind: "output", text: "TCP    127.0.0.1  5173  18510  vite      LISTEN  -" },
    { kind: "output", text: "TCP    0.0.0.0    5432  1201   postgres  LISTEN  postgres" },
  ]}
/>

The table is plain whitespace-separated text with no box drawing, so `grep` and `awk` handle it
fine. Missing details show as `-`. The `LABEL` column appears once you configure
[endpoint labels](/docs/config#endpoint-labels).

Notes on stderr explain what the table can't. Each `-` in the PID column gets a reason: the socket
belongs to another user whose processes you can't read (named by account on Linux, such as
`root (uid 0)`), its owner couldn't be attributed, or no readable process holds it at all, which is
normal for kernel-held sockets. On Linux, a process whose executable was deleted or replaced after
it started is listed with its original path; that usually means a stale build or a leftover from a
package upgrade. Stdout stays a clean table.

<Terminal
  title="kick list"
  lines={[
    { kind: "command", text: "kick list" },
    { kind: "muted", text: "PROTO  ADDRESS    PORT  PID    PROCESS  STATE" },
    { kind: "output", text: "TCP    127.0.0.1  3000  18422  devsrv   LISTEN" },
    { kind: "output", text: "TCP    127.0.0.1  5432  -      -        LISTEN" },
    { kind: "muted", text: 'note: PID "-" means the socket\'s owner is not visible:' },
    {
      kind: "muted",
      text: "  1 row(s) belong to other users (postgres (uid 970): 1); at least 412 process(es) could not be read (permission denied). Rerun with sudo to see their owners.",
    },
    {
      kind: "muted",
      text: "note: 1 listed process(es) run an executable that was deleted or replaced after they started (often a stale build or an upgraded package):",
    },
    { kind: "muted", text: "  PID 18422 (devsrv): /home/me/app/target/debug/devsrv" },
  ]}
/>

Human-readable output keeps the IPv6 interface, as in `[fe80::1%3]:5353`, everywhere: the table,
the TUI, `inspect`, `watch`, `why`, search, diagnostics, and kill confirmations. Linux and macOS
can't report the interface, so their IPv6 addresses show no suffix. Legacy `list --json` doesn't
change; the versioned JSON formats carry the scope in its own field.

### Narrowing the list

<CommandBlock
  code={
    "kick list --port 3000\nkick list --process node\nkick list --filter scope:public\nkick list --filter 'label:web family:ipv4'\nkick list --sort pid"
  }
  label="list options"
/>

- `--port PORT` keeps only rows bound to that exact port.
- `--process TEXT` keeps rows whose process name contains the text.
- `--filter TEXT` takes the same search text or structured terms as the TUI (see
  [filters](/docs/commands#filters)).
- `--sort MODE` sorts by `port`, `pid`, `protocol`, `process`, `parent`, or `scope`.

## JSON for scripts

`list --json` prints a documented shape. Its field names and enum spellings are a contract, so you
can parse it safely.

<Terminal
  title="kick list --port 3000 --json"
  lines={[{ kind: "command", text: "kick list --port 3000 --json" }]}
/>

```json
[
  {
    "protocol": "tcp",
    "local_addr": "127.0.0.1",
    "local_port": 3000,
    "state": "listen",
    "pid": 18422,
    "process_name": "node",
    "executable_path": "/usr/bin/node",
    "command_line": "node server.js",
    "parent_pid": 18001,
    "parent_process_name": "cursor-agent",
    "child_pids": [],
    "protected": false,
    "platform": "linux",
    "permission": "full",
    "label": "web dev"
  }
]
```

Missing details are `null`, never an empty string. An empty result is always `[]`.

For everything the collector saw, including every TCP state, owner identity, completeness, and
evidence gaps, use `--snapshot-json`:

<CommandBlock code={"kick list --snapshot-json"} label="full snapshot" />

Snapshot mode can't be combined with `--port`, `--process`, `--filter`, or `--sort`, ignores
`hide_system_processes`, and leaves out full command lines. See
[Structured output](/docs/structured-output).

## Killing by port or PID

`kill` takes ports or PIDs, one or several, and asks before it does anything.

<Terminal
  title="kick kill --pid 18422"
  lines={[
    { kind: "command", text: "kick kill --pid 18422" },
    { kind: "output", text: "Terminate PID 18422 (node)" },
    { kind: "output", text: "Scope: process" },
    { kind: "output", text: "Ports: TCP 127.0.0.1:3000" },
    { kind: "output", text: "Command: kill 18422" },
    { kind: "muted", text: "Type y to confirm, or press Enter to cancel: y" },
    { kind: "success", text: "sent SIGTERM to PID 18422 (node)" },
    { kind: "success", text: "PID 18422 (node) exited" },
    { kind: "success", text: "confirmed target ports are no longer visible" },
  ]}
/>

A delivered signal doesn't mean the process exited, and a closed listener doesn't either. After
delivery, `kill` waits up to two seconds and reports both on their own lines. If a server closes
its listener but keeps running, Kickoutchi warns you and prints the command that sends `SIGKILL`:
`kick kill --pid PID --force` while it still owns its port, or `kick kill --pid PID --tree --force`
once the port is closed, since a plain `--pid` kill no longer applies then. The `--tree` form also
stops the process's children. Either way, the exit code means the signal was accepted.

On Linux, an unprivileged `kill --port` usually can't read other users' processes, so it can't
prove that no hidden process shares the socket. If the port has no readable owner, `kill --port`
refuses before any prompt (exit `4`). If it finds one verified owner and only unrelated processes
are unreadable, it prints a note and targets that owner. Before sending, it checks the port again
for a second visible owner, and afterwards it reports whether the port cleared.

<CommandBlock
  code={
    "kick kill --port 3000\nkick kill --pid 18422\nkick kill --port 3000 --yes\nkick kill --pid 18422 --force"
  }
  label="kill examples"
/>

- `--force` asks for the stronger `force` confirmation. Unix sends `kill -9`; on Windows every kill
  is a hard termination anyway.
- `--yes` skips the normal prompt for a target you already trust.

### Several targets at once

Repeat `--pid` or `--port`, or separate values with commas, to stop up to 128 processes in one
command. Kickoutchi resolves every target first. If any target is unresolved, protected, or can't be
shown to own its port, it lists the refusals and sends nothing. Otherwise you get one banner, one
prompt, and one summary line, plus a line each for failures, survivors, and ports still open.

<Terminal
  title="kick kill --pid 18422,18510,18611 --yes"
  lines={[
    { kind: "command", text: "kick kill --pid 18422,18510,18611 --yes" },
    { kind: "output", text: "Terminate 3 processes:" },
    { kind: "output", text: "  PID 18422 (node): TCP 127.0.0.1:3000" },
    { kind: "output", text: "  PID 18510 (vite): TCP 127.0.0.1:5173" },
    { kind: "output", text: "  PID 18611 (node): TCP 127.0.0.1:4000" },
    {
      kind: "success",
      text: "summary: sent SIGTERM to 3 of 3 process(es); 3 exited; 3 of 3 confirmed port(s) no longer visible; 0 failed",
    },
  ]}
/>

Each target still gets every single-process check. The exit code is the most serious outcome across
all targets. `--tree` and `--group` take a single target.

<Callout type="safety" title="What --yes does and doesn't do">
  `--yes` stops Kickoutchi from asking, not from telling. The target banner and every warning still
  print, and it can't skip protected-process confirmation: a protected target with `--yes` exits
  with code `6` and nothing is signalled.
</Callout>

On Linux and macOS, Ctrl-C during a kill waits for frozen processes to be cleaned up. If delivery
hasn't started, Kickoutchi stops and resumes only the processes it froze; anything that was already
stopped stays stopped. Once delivery has started, it finishes delivery and cleanup before the
interrupt takes effect. This holds for single, tree, and group kills, and for `SIGTERM` and `SIGHUP`
sent to the CLI.

## Inspecting a process family

`inspect` is the read-only way to pick the right root before a scoped kill. It shows ancestors,
descendants, siblings, command lines, ports, and suggested tree commands. Linux and macOS also show
process-group members and `--group` hints.

  code={"kick inspect --port 3000\nkick inspect --pid 18422"}

## Tree and group scope

A normal kill targets one PID. `--tree` also stops its descendants, on Linux, macOS, and Windows.
`--group` stops a POSIX process group, on Linux and macOS:

<CommandBlock
  code={"kick kill --port 3000 --tree\nkick kill --pid 18422 --tree\nkick kill --pid 18422 --group"}
  label="scoped kill examples"
/>

- `--tree` stops the target and its descendants. Type `tree` to confirm, or `force` with `--force`.
- `--group` stops every visible member of the target's process group. Type `group` to confirm, or
  `force` with `--force`.
- `--tree` and `--group` can't be combined.
- Windows rejects `--group` and has no TUI `t` / `T` keys. Its CLI `--tree` contains the tree in a
  Job Object and terminates it outright.

[Scoped kills](/docs/scoped-kills) explains how Unix freezes the tree first and how Windows uses Job
Objects.

## Watching and explaining

Two read-only commands answer questions `list` can't:

<CommandBlock
  code={
    "kick why 3000\nkick why 3000 --all-protocols --all-addresses --json\nkick watch --tcp --port 3000\nkick watch --filter state:listen --duration 30s --json"
  }
  label="watch and why"
/>

- `why PORT` takes one snapshot, tries an exact bind, and releases it at once. It prints one line
  per endpoint (who holds it, or `free`) and tells apart in use, permission denied, address
  unavailable, and unsupported. `--verbose` shows the evidence behind each verdict.
- `watch` polls snapshots and streams `baseline`, `bind`, `release`, `replacement`, and
  `collection_gap` events, as text or NDJSON.

Neither one signals a process. The full walkthrough is in [Watch & Why](/docs/watch-and-why).

## How the CLI behaves

- An empty unfiltered list is a success (exit `0`). A quiet machine isn't an error.
- An empty filtered result is a no-match (exit `3`), so `kick list --port 3000 && echo busy` works
  as a quick "is this port taken?" check.
- `kill --port` refuses a port two PIDs share. It lists the candidates and asks you to pick one
  with `--pid`.
- A port with no readable owner exits `4` (permission denied) and says why, such as "the socket
  belongs to another user".

When `--port` finds no socket but some process mentions that port on its command line, Kickoutchi
prints a "possible related process" hint on stderr, so JSON on stdout stays clean.
