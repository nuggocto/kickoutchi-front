Start with the exact message or symptom below. Most cases come from socket state, operating-system
permissions, or a safety check refusing an uncertain target.

## A port shows in another tool but not in Kickoutchi

`list` and the TUI show listening TCP and bound UDP sockets, the states that hold a local port.
They leave out established and in-between connections on purpose, so a port another tool shows may
not be a listener. Kickoutchi also reads the OS directly instead of parsing `ss`, `netstat`, or
`lsof`, so its output can differ from theirs.

Kickoutchi does collect every socket state; the table just doesn't show them all.
[`kick list --snapshot-json`](/docs/structured-output) and
[`kick watch`](/docs/watch-and-why) both keep every TCP state, including `established`,
`time_wait`, and the in-between ones.

## Process metadata is missing (shows `-`)

The socket is visible, but Kickoutchi couldn't read its owner or some of the owner's details,
usually because the process belongs to another user. `kick list` explains every `-` row in notes on
stderr: a socket that belongs to another user (named by account on Linux, such as `root (uid 0)`), a
socket whose owner wasn't attributed, or a socket no readable process holds, which is normal for
kernel-held sockets. Run again with `sudo` to fill in the owners. JSON keeps the row, with `null`
fields and `"permission": "partial"`.

## `kill --port` prints a note about unreadable processes

On Linux, an unprivileged user can't read other users' processes, so Kickoutchi can't prove that
nobody else shares the port's socket. When the port has one verified owner, it prints a note and
targets that owner by PID, with the same checks as `kick kill --pid`. If a hidden process does share
the socket, the after-kill report says the port is still visible; rerun with `sudo` to see it. A
port whose owner itself can't be read is still refused, with the reason.

## Permission denied when killing

You don't have the rights to signal that process (exit `4`). On Linux and macOS, try `sudo`; on
Windows, use an elevated terminal. If a `--port` target has no readable owning PID, Kickoutchi reports
permission denied rather than guessing, and says why, for example that the socket belongs to
another user.

## `kill` says the process is still running

The signal was delivered, but the process hadn't exited two seconds later. Servers often close their
listener first and finish shutting down afterwards, so the port can be free while the process is
still alive. Wait and check again, or run the command the warning prints to send `SIGKILL` on Linux
and macOS. If the process closed its port, that command uses `--tree`, because a plain `--pid` kill
only targets port owners. The exit code is still `0`, because the signal was accepted.

## `kill --pid` says the PID "still exists but owns no visible open port"

A plain `kick kill --pid` only targets a process that owns a visible port, so a typo'd or unrelated
PID can't be killed by accident. The process is alive but has no listener, often because it closed
it during shutdown. Run the suggested `kick kill --pid PID --tree` (add `--force` for `SIGKILL`); it
also stops the process's children, so check them first with `kick inspect --pid PID`.

## A batch kill sent nothing

With several targets, Kickoutchi resolves and authorizes every one before sending any signal. If a
single target is unresolved, protected, or can't be shown to own its port, it refuses the whole
batch and lists each refusal. Fix or drop those targets and rerun. Kill protected processes
on their own so they can be confirmed by PID or name.

## A process "runs an executable that was deleted or replaced"

The binary file on disk changed after the process started. After a rebuild, this usually means an
old dev server is still running from the previous build. After a system upgrade, it means a daemon
is running the pre-upgrade binary. `kick inspect --pid PID` shows the original path and the process
family, and notes when init or a service manager adopted the process, a sign that its launcher
exited and left it orphaned.

## A protected process asks for stronger confirmation

That's protection working. Type the PID or the process name to confirm. You can add names with
[`protected_processes`](/docs/config#protected-processes), but you can't remove the built-in ones,
and they're there for good reasons.

## `kill --port` says the target is ambiguous

Two or more PIDs own that port, so Kickoutchi won't guess. It prints the candidates; run again with
`--pid` and the one you mean.

## `why` says the port is free, but my server still can't bind

There are three usual causes, and the per-endpoint rows tell you which:

- A different address. `why 3000` checks `127.0.0.1` and `::1` by default, but your server may bind
  `0.0.0.0` or a LAN address. Run again with `--all-addresses` or an explicit `--address`.
- A different protocol. The default is TCP; add `--udp` or `--all-protocols`.
- A race. A successful probe binds and releases at once. It proves the endpoint was free at that
  instant but doesn't reserve it, and something else can take it a millisecond later.

## `why` says `owner_hidden`

The endpoint is in use and a process probably holds it, but your account can't see which one,
usually because it belongs to another user. On Linux the evidence names the UID that created the
socket. Run again with `sudo` to find the owner.

## `why` exits `4` for a low port

Binding a port below 1024 usually needs elevation, so the OS refuses the probe before it learns
anything. Kickoutchi reports `permission_denied` rather than guessing "free" or "busy", because it
really doesn't know. Run it elevated if you need an answer.

## `watch` printed `collection_gap`

A poll failed. Kickoutchi keeps the last good snapshot and retries, so the failure can't turn into a
wave of false `release` events. If three polls in a row fail, `watch` prints the third gap, explains
on stderr why it stopped, and exits `1`. Gaps ignore your filters on purpose, so you always find out
when watch stopped seeing.

## `watch` shows `filter=indeterminate`

Your filter needed something Kickoutchi couldn't read, usually an owner PID or a process name behind
a permission boundary. Instead of dropping the event, watch prints it marked indeterminate, so you
know a filter might have hidden something. Definite non-matches are still hidden. If you only care
about definite matches, for example while following one PID, add `--matched-only` to drop the
indeterminate events.

## `watch` missed a port that definitely opened

`watch` polls; it doesn't receive kernel events. A socket that opens and closes between two polls is
never seen, and several changes can collapse into one net difference. A lower `--interval` (down to
`100ms`) narrows that window but can't close it.

## My label isn't showing up

- The CLI and TUI only show a `LABEL` column when at least one label is configured. The TUI also
  needs a wide enough terminal. Structured output always carries the label.
- Selectors are exact: `protocol`, `address`, and `port` must all match, and TCP and UDP are
  separate. Use `address = "*"` to match any address for a protocol and port.
- An exact selector always wins over a wildcard for the same endpoint.
- Hostnames, CIDR ranges, interface names, and `%zone` syntax are rejected; use `scope_id` for an
  IPv6 scope.

See [Endpoint labels](/docs/config#endpoint-labels) for the validation rules.

## Linux: kernel too old for pidfd termination

Listing ports works on older kernels, but stopping a process needs Linux 5.3 or newer, because
Kickoutchi sends the signal through a `pidfd`. That ties the signal to the exact process, so a
recycled PID can't be hit by mistake.

## Windows: some processes need an elevated terminal

Higher-privilege processes can hide their details or refuse termination from a normal shell. Open
your terminal as administrator and try again.

## macOS: process identity changed before termination

macOS has no pidfd, so Kickoutchi re-checks the process identity right before signalling. If the PID
now belongs to a different process than the one you confirmed, it refuses and sends nothing. List
again and retry.

## Linux/macOS tree/group kill says it thawed everything

The tree or group kill hit a safety refusal after it started freezing: permission denied, a changed
identity, a protected descendant, incomplete metadata, a scope over the limit, or a membership that
kept changing. Kickoutchi sent `SIGCONT` to every member it had stopped and sent no termination
signal.

If a cleanup error names PIDs, their `SIGCONT` was refused and they may still be stopped, so check
them. A member that exited while frozen isn't listed, because there's nothing left to resume.

## Windows tree kill reports incomplete metadata or partial containment

Windows has no `SIGSTOP`, so a tree kill checks everything before it assigns the tree to a Job
Object, and refuses if missing creation-time data could hide a descendant. After that it proves the
final job membership again before terminating. If a live member can't join the job, it terminates
nothing, because killing that one process on its own would let its children escape the job. A tree
that keeps starting processes during the final check is refused; run the kill again. Delivered,
already exited, unconfirmed, and not terminated PIDs are reported separately instead of all as
"success".

## Windows: `--group` or TUI `t`/`T` is unavailable

That's expected. Windows has read-only `inspect` and CLI `--tree`, but `--group` needs POSIX
process groups, and the Windows TUI leaves out the tree keys. If `inspect` or CLI `--tree` is
unknown on Windows, run `kick --version` and update to the latest release.

## The TUI kept running after I closed its terminal

Kickoutchi 1.3.1 through 1.7.1 could survive a closed terminal window, spin a CPU core, and ignore
`SIGTERM`, which made a reboot wait for systemd's stop timeout before it sent `SIGKILL`. Version
1.7.2 fixes this. Until you upgrade, quit with `q` before closing the window, or end a leftover
with `pkill -KILL -x kick` (or `kickoutchi`). A TUI started with `SIGHUP` ignored, for example
under `nohup`, can still linger after its window closes.

## The TUI says "Terminal too small"

The table needs at least 80×20. Make the window bigger (or zoom out your terminal font) and the UI
comes back.

## `kickoutchi-update` is missing

The installer has shipped the updater since 0.1.2. If you installed earlier, or another way, run
the latest installer once; after that, `kickoutchi-update` handles upgrades.
