Field names and enum values use lowercase `snake_case`. The newer formats name their schema and an
integer version inside the document; legacy list JSON keeps its original bare array.

| Command                     | Contract                   | Form       |
| --------------------------- | -------------------------- | ---------- |
| `kick list --json`          | `kickoutchi.list/1`        | JSON array |
| `kick list --snapshot-json` | `kickoutchi.snapshot/1`    | One object |
| `kick watch --json`         | `kickoutchi.watch_event/1` | NDJSON     |
| `kick why PORT --json`      | `kickoutchi.why/1`         | One object |

Snapshot, watch, and why carry the names shown above. `list --json` stays a bare top-level array so
existing scripts keep working.

Diagnostics always go to stderr, so stdout stays parseable.

## `kickoutchi.list/1`: the compatibility array

`list --json` prints the rows you'd see in the table. It applies `--port`, `--process`, `--filter`,
`--sort`, and `hide_system_processes`, and lists only listening TCP and bound UDP sockets.

```json
[
  {
    "protocol": "tcp",
    "local_addr": "127.0.0.1",
    "local_port": 3000,
    "state": "listen",
    "pid": 18422,
    "process_name": "node",
    "executable_path": "/usr/bin/node",
    "command_line": "node server.js",
    "parent_pid": 18001,
    "parent_process_name": "pnpm",
    "child_pids": [],
    "protected": false,
    "platform": "linux",
    "permission": "full",
    "label": "web dev"
  }
]
```

`label`, added in 1.3.0 and nullable, is the only field ever added to this format.

<Callout type="note" title="child_pids is frozen">
  `child_pids` stays only for `1.x` compatibility. It's `[]` on every row and every platform, with
  no data behind it. Use `kick inspect` to see a real process family.
</Callout>

Missing metadata is `null`, never an empty string. An empty result is `[]`.

## `kickoutchi.snapshot/1`: the full observation

`list --snapshot-json` prints one object describing everything Kickoutchi could see within its
platform's scope. It skips list filters, sorting, `hide_system_processes`, and the
listening-TCP/bound-UDP view on purpose, and it never includes full command lines.

<CommandBlock code={"kick list --snapshot-json"} label="full snapshot" />

Top-level keys:

| Key                          | Contains                                                          |
| ---------------------------- | ----------------------------------------------------------------- |
| `schema` / `version`         | `"kickoutchi.snapshot"` and `1`.                                  |
| `scope`                      | The scope's `kind`, an `identifier`, and its fixed `limitations`. |
| `completeness`               | `complete`, `partial`, or `raced`, within that scope.             |
| `owner_completeness`         | Whether owner attribution across the snapshot is complete.        |
| `capture`                    | When collection started and finished.                             |
| `sockets`                    | Every endpoint, with state, timer evidence, owners, and label.    |
| `processes`                  | Identities, names, paths, parents, and metadata completeness.     |
| `evidence_gaps`              | What could not be established, and what each gap affects.         |
| `omitted_evidence_gap_count` | How many gaps didn't fit under the output limit.                  |

A socket entry looks like this:

```json
{
  "endpoint": { "protocol": "tcp", "address": "127.0.0.1", "port": 3000, "ipv6_scope": null },
  "state": { "kind": "listen", "native_code": null },
  "timer": {
    "kind": "none",
    "native_code": null,
    "raw_ticks": 0,
    "estimated_remaining_milliseconds": 0,
    "certainty": "estimated"
  },
  "owners": {
    "owners": [
      {
        "kind": "verified",
        "identity": {
          "pid": 18422,
          "start_marker": { "kind": "linux_start_ticks", "ticks": 11977192 }
        }
      }
    ],
    "omitted_owner_count": 0,
    "completeness": "complete",
    "reasons": []
  },
  "socket_token": { "kind": "linux_inode", "value": 1631547 },
  "label": "web dev"
}
```

An owner is either `verified` (a PID plus its start time) or marked as an unverified PID. That
difference matters, because a bare PID doesn't identify a process for long: the OS reuses PIDs.

### Evidence gaps and affected PID counts

Every `EvidenceGap` has a nullable `pid` and a nullable `affected_pid_count`, both always present.
A gap about one known PID sets `pid` and leaves `affected_pid_count` null. When a Linux scan loses
data for several PIDs that aren't known to hold the target socket, a single gap sets a positive
`affected_pid_count` and leaves `pid` null.

If several passes see the same loss, Kickoutchi keeps the largest count rather than adding them up,
since they may describe the same PIDs. `omitted_evidence_gap_count` is a different thing: it counts
gap records that didn't fit in the output array, never PIDs.

## `kickoutchi.watch_event/1`: one object per line

`watch --json` writes NDJSON. Each line is valid JSON on its own and at most 64 KiB, so a streaming
reader never has to buffer the whole session.

```json
{
  "schema": "kickoutchi.watch_event",
  "version": 1,
  "sequence": 0,
  "event": "bind",
  "observation": {
    "previous_completed_unix_ms": 1784929159673,
    "attempt_started_unix_ms": 1784929159955,
    "attempt_completed_unix_ms": 1784929159972
  },
  "data": {
    "endpoint": { "protocol": "tcp", "address": "127.0.0.1", "port": 3000, "ipv6_scope": null },
    "state": { "kind": "listen", "native_code": null },
    "previous_owners": null,
    "current_owners": {
      "owners": [
        {
          "kind": "verified",
          "identity": {
            "pid": 18422,
            "start_marker": { "kind": "linux_start_ticks", "ticks": 11977192 }
          }
        }
      ],
      "omitted_owner_count": 0,
      "completeness": "complete",
      "reasons": []
    },
    "previous_socket_token": null,
    "current_socket_token": { "kind": "linux_inode", "value": 1631547 },
    "multiplicity": 1,
    "label": "web dev",
    "filter_result": "matched",
    "certainty": "proven",
    "evidence": [],
    "omitted_evidence_count": 0,
    "evidence_gaps": [],
    "omitted_evidence_gap_count": 0
  }
}
```

- `event` is `baseline`, `bind`, `release`, `replacement`, or `collection_gap`.
- `sequence` counts up by one per record, so a missing record shows as a gap.
- `observation` brackets a collection attempt, not the exact moment of the change.
- `previous_owners` and `current_owners` are what make a `replacement` event useful.
- `filter_result` is `not_applied`, `matched`, or `indeterminate`; see
  [Watch & Why](/docs/watch-and-why#filtering).

Records never include full command lines.

## `kickoutchi.why/1`: one document

`why --json` prints one object with the same verdicts, certainty, evidence, gaps, labels, and
overall exit code as `--verbose` text output. It never collects full command lines.

Why writes the document as a stream, so a valid result is never refused for its total size.

## Privacy

<Callout type="warning" title="Escaping is not redaction">
  Structured output can expose endpoints, PIDs, process identities, names, executable paths, labels,
  ownership, and evidence. Legacy `list --json` can also include full command lines, which often
  contain tokens, paths, and connection strings.

Terminal sanitizing makes output safe to display. It doesn't remove anything sensitive. Treat these
documents like `ps` output before you paste them into an issue or send them to a log service.

</Callout>

## Keep these apart

Kickoutchi goes to some trouble to keep these separate, so don't merge them when you read the
output:

- `null`, empty, and omitted are three states: unknown, known to be empty, and dropped by a limit.
- `complete` means complete within the platform's scope, not every socket in every container,
  namespace, VM, or subsystem. `partial` means some of it couldn't be read.
- Only a verified owner identity survives PID reuse; an unverified PID doesn't.
- Certainty belongs to the one claim carrying it, not to the whole document.
